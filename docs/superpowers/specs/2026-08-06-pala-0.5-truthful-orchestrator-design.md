# Pala Project Studio 0.5 — Kanıtlı Orkestratör Tasarımı ve Tavsiye Mektubu

- Durum: Üretici incelemesine sunulan tasarım
- Kanıt kesiti: 2026-08-06, kaynak commit `58c12a4`
- Hedef sürüm: `0.5.x`
- Hedef kullanıcı: Yardımcı araç adlarını bilmeyen, sonucu ve kanıtı görmek isteyen yazılım üreticisi

## Üreticiye mektup

Pala Project Studio'nun gerçek değeri modele daha fazla zekâ veya token vermek
değil; dağınık bir yazılım işini güvenli, devam ettirilebilir ve kanıtlanabilir
bir çalışma akışına çevirmektir. Mevcut `0.4.4` sürümü kurulum, atomik dosya
yazımı, secretsız durum, doğrulama katmanları ve yönetilen araç bütünlüğünde
çalışan bir temel sunuyor. Aynı kaynak kesitinde 154 testin geçmesi bu temelin
regresyon disiplinini kanıtlıyor.

Ancak ürünün “tek kapı” ve “gereken uzmanı seçer” vaadi henüz uçtan uca
kanıtlanmıyor. Durum okuyucuları aynı projede farklı gerçekler üretebiliyor;
bağlı Git worktree'leri ortak bir depo olarak uzlaştırılmıyor; v2 ve v3 ticket
kayıtlarının önceliği belirsiz; uzman yönlendirici karar üretiyor fakat çalışma
zincirine bağlı değil; MCP adaptörü güncel Codex çıktısını yanlış yorumluyor;
varsayılan kurulum ise yaklaşık 0,39 MiB'lık çekirdeğin yanında bu makinede
6 GiB'ı aşan uzman alanı oluşturmuş durumda.

Bu nedenle `0.5` için önerim “daha çok araç çalıştıran Pala” değil, **doğru
çalışma kopyasını bulan, tek proje fotoğrafı çıkaran, en küçük yeterli uzmanı
seçtiğini açıklayan ve sonucu insan dilinde kanıtlayan Pala**dır. Pluginlerin
kendileri çalışma zamanı aracı değildir; Codex ilgili skill, MCP, app veya yerel
aracı seçer. Pala bu seçimi koordine etmeli, uzmanların güvenlik sözleşmesini
devralmamalı ve her göreve gereksiz uzman yükü bindirmemelidir.

## Kanıt yöntemi

Bu belgede bir öneri yalnız aşağıdakilerden en az biriyle destekleniyorsa yer
alır:

1. Kaynak committe dosya ve satır/fonksiyon kanıtı.
2. Aynı gün çalıştırılan, salt-okunur veya proje doğrulama komutu sonucu.
3. Güncel resmî Codex manualindeki ürün sözleşmesi.

Ölçüm hedefleri gelecekteki kabul kapılarıdır; gerçekleşmiş kazanım gibi
sunulmaz. Yerel kullanıcı yolu ve özel proje adı kalıcı belgeye yazılmamıştır.
Gerçek çok-worktree vakası uygulama testine anonimleştirilmiş fixture olarak
alınacaktır.

## Değerlendirilen yaklaşımlar

### A — Yalnız talimat ve README yaması

En ucuz seçenektir. Skill metnine daha sert “uzman seç” cümlesi ekler ve insan
dilini iyileştirir. K05, K08, K09 ve K14 gibi yürütülebilir kusurları çözmediği
için ürün vaadini kanıtlayamaz. Önerilmez.

### B — Truth-first, Codex-native orkestratör

Önerilen yaklaşımdır. Ayrı bir Pala MCP sunucusu eklemeden mevcut skill, hook ve
deterministik Python yapısını korur; tek `ProjectSnapshot`, worktree-aware durum,
tek yönlendirme sözleşmesi, insan sunumu ve uçtan uca eval ekler. ADR-001'in
küçük güven yüzeyini korurken gerçek kusurları çalıştırılabilir testlerle kapatır.

### C — Pala-owned MCP ve görsel Project Home ile başlamak

Yapılandırılmış araçlar, gözlemlenebilirlik ve görsel gezinme sağlayabilir;
ancak yeni sunucu yaşam döngüsü, paketleme, güven, yüzey uyumluluğu ve test yükü
oluşturur. Resmî mimari rehberi mevcut araçlar ve talimat yeterliyse skill ile
başlamayı önerir. `0.5` ölçümleri skill+script çözümünün yetersiz olduğunu
göstermeden bu maliyet alınmayacaktır; karar `0.6`ya ertelenir.

## Önerilen mimari

```text
Kullanıcı isteği
  -> Pala görev modu ve mevcut oturum capability kataloğu
  -> SnapshotBuilder
       -> RepoIdentity + WorktreeIdentity
       -> v3 ticket'lar + legacy v2 gözlemi
       -> kayıtlı belge sözleşmesi + Git basis
       -> typed reconciliation findings
  -> CapabilityBroker
       -> direct | exact skill | MCP/app | Pala-managed expert
       -> RoutingDecision + güvenli fallback
  -> Codex seçilen alt kabiliyeti yürütür
  -> EvidenceNormalizer
  -> Human/Markdown çıktı veya sürümlü JSON
```

Temel veri sözleşmeleri:

- `RepoIdentity(common_dir_digest)` ortak Git deposunu tanımlar; mutlak özel yol
  kalıcı kayda girmez.
- `WorktreeIdentity(root, git_dir_digest, branch, head)` yalnız runtime
  sunumunda mutlak yolu kullanır.
- `ProjectSnapshot` kayıtlı belgeleri, durable ürün fazını, bütün aktif
  ticket'ları, worktree'leri, Git basis'i ve typed bulguları tek immutable
  sonuçta birleştirir.
- `ReconciliationFinding(code, severity, source, expected, observed, action)`
  boolean ve serbest metin yerine kararlı hata sözleşmesidir.
- `RoutingDecision(task_class, target_kind, target_id, availability,
  reason_code, fallbacks, authority)` plugin adı “çalıştırmaz”; Codex'in
  kullanacağı exact alt skill/tool/app veya `direct` yolunu açıklar.

Devam hedefi seçim sırası:

1. Kullanıcının açık `--worktree` veya mevcut sohbet worktree'si.
2. Mevcut session'ın sahip olduğu dirty v3 ticket.
3. Ortak depoda yalnız bir adet uyumlu aktif ticket.
4. Çelişkisiz mevcut worktree checkpoint'i.
5. Birden fazla aday varsa tahmin yok; adaylar ve uzlaştırma eylemi gösterilir.

Durable durum belgesi ürün fazını, v3 kaydı canlı oturum sahipliğini taşır.
Birbirleriyle çelişirlerse Pala ikisini de gösterir ve tamamlanmış/aktif sonucu
uydurmaz. Migration marker sonrası v2 yalnız audit/rollback girdisidir.

## Sürüm dilimleri

Bu kapsam tek dev ticket değildir. Onaydan sonra dört ayrı executable plan
hazırlanır ve sırayla yürütülür:

1. **0.5A — Truth Core:** Öneri 1-13; snapshot, worktree, state migration,
   checkpoint ve insan durumunun veri temeli.
2. **0.5B — Routing Core:** Öneri 14-26; capability broker, gerçek uzman
   yürütmesi, MCP uyumu ve E2E seçim testleri.
3. **0.5C — Human/Core Delivery:** Öneri 27-31 ve 35; human/Markdown çıktı,
   Core/Expert ayrımı, hızlı hook ve erişilebilir kurulum.
4. **0.5D — Evidence Release Gate:** Öneri 32-34; Goal karşılaştırması,
   benchmark, claims registry ve release doğruluğu.

Her dilim bağımsız testlenebilir ve önceki dilimin public arayüzlerini tüketir.
Bir dilim başarısızken sonraki dilim ürün vaadini genişletmez.

## Hata ve güvenlik davranışı

- Bilinmeyen Codex JSON şeması `missing` değil `unsupported_schema`dır.
- Birden fazla worktree adayı varsa Pala seçim yapmaz; güvenli adayları listeler.
- Uzman unavailable/timeout/invalid-output durumunda kaynak/test ile doğrulanan
  en küçük fallback'e döner ve sebebi gösterir.
- Hook; ağ, install, test, build, uzman process'i veya GitHub mutasyonu başlatmaz.
- Route kaydı ham prompt, query, kod, transcript, secret veya mutlak özel yolu
  kalıcılaştırmaz; bounded sınıflandırma ve sonuç kodu taşır.
- Migration eski v2 dosyasını silmez veya değiştirmez; yeni state atomik yazılır.
- Commit, push, PR, tag, release ve deploy ayrı yetki olarak kalır.

## Test stratejisi

1. Saf model testleri: identity, snapshot, precedence, finding ve route tabloları.
2. Gerçek geçici Git testleri: linked worktree, detached HEAD, branch rename,
   pruned worktree, Windows path/case ve divergent branches.
3. State migration testleri: v2/v3 çelişkisi, idempotency, crash/rollback,
   session isolation ve tracked-state doctor.
4. Adapter testleri: gerçek Codex 0.146.0 fixture'ı, legacy schema, alias,
   disabled/foreign record ve fail-fast olmayan Doctor.
5. Uzman E2E testleri: stub executable, timeout, invalid JSON, evidence
   normalization ve direct fallback.
6. Plugin eval: portable install sonrası yeni konuşmada direct/indirect/follow-up/
   negative/specialist-precedence istemleri.
7. İnsan çıktı golden testleri: Türkçe, plain, Markdown link, sekiz satır bütçesi
   ve makine JSON geriye uyumu.
8. Release benchmark: üç kol, her görev/kol için en az 10 tekrar ve ham sonuç
   arşivi. Ölçülmeyen kazanç README'ye yazılmaz.
